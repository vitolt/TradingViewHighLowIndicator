## 📋 Основные правила работы с проектом

### Правило 1: Всегда использовать субагента для сборки проекта

**Описание**: При выполнении задачи полной сборки или переборки проекта HighLow.pine ВСЕГДА использовать субагента вместо прямого редактирования.

**Причина**: Субагент может параллельно:
- Проверить все требования из REQUIREMENTS.md
- Применить все исправления из ERRORS_LOG.md
- Обновить версию в заголовке файла
- Проверить синтаксис Pine Script v5
- Обновить документацию

**Процесс**:
```
Задача сборки → Создать субагента → Субагент исправляет проект → Уведомление о завершении
```

**Когда применять**:
- Полная переборка проекта
- Обновление версии
- Исправление критических ошибок
- Синхронизация требований и кода

---

### Правило 2: REQUIREMENTS.md содержит описание требований

**Описание**: Файл `REQUIREMENTS.md` является источником истины для функциональности индикатора.

**Содержимое**:
- Описание проекта и функциональности
- Основная логика отображения (видимость, пересечение, ТФ фильтр)
- Параметры настройки индикатора
- Расчёты и логика
- Требования к интерфейсу
- Поддерживаемые инструменты
- Таблица статуса реализации

**Использование**:
1. Перед началом работы - прочитать требования
2. При сборке проекта - используется как контрольный список
3. При добавлении новых функций - обновить требования
4. Синхронизировать с кодом (правило из MEMORY.md)

**Версионирование**: 
- Версия в REQUIREMENTS.md → соответствует версии HighLow.pine

---

### Правило 3: ERRORS_LOG.md содержит описание ошибок и способы их исправления

**Описание**: Файл `ERRORS_LOG.md` документирует все ошибки, которые возникали при разработке, и их решения.

**Содержимое**:
- Ошибка 1-6: Описание проблемы, причина, решение
- Справочники: работа с массивами UDT, функции Pine v5, синтаксис
- Чек-листы проверки перед компиляцией
- Таблицы сравнения правильного vs неправильного синтаксиса

**Использование при сборке**:
1. Прочитать все ошибки (Ошибка 1-6)
2. Проверить, что код их не содержит
3. Применить все решения из справочников
4. Использовать чек-листы для финальной проверки

**Пример критических ошибок**:
- ❌ `var line ln` в типе → ✅ `line ln` (без var)
- ❌ `Level.new(..., na(line))` → ✅ `Level.new(..., dummy_line)`
- ❌ `if ta.change(time("D"))` → ✅ `if ta.change(time("D")) != 0`
- ❌ `lvl = array.get(...); lvl.field := val;` → ✅ `lvl = array.get(...); lvl.field := val; array.set(levels, i, lvl);`

## 🔧 Технические правила Pine Script v5

### Тип Level (корректное использование)

```pine
// ✅ ПРАВИЛЬНО
type Level
    float price
    string label_tags
    int start_bar
    int cross_bar
    bool is_high
    string level_type
    line ln        // БЕЗ var
    label lb       // БЕЗ var

// ✅ Глобальные переменные
var array<Level> levels = array.new<Level>()
var line dummy_line = na
var label dummy_label = na

// ✅ Конструктор с 8 аргументами
new_lv = Level.new(price, tags, bar_index, 0, is_high, type, dummy_line, dummy_label)
```

### Работа с UDT в массивах

```pine
// ✅ ПРАВИЛЬНО
lvl = array.get(levels, i)
lvl.cross_bar := bar_index
array.set(levels, i, lvl)  // ← ОБЯЗАТЕЛЬНО!

// ❌ НЕПРАВИЛЬНО
lvl = array.get(levels, i)
lvl.cross_bar := bar_index  // Изменение не сохранится без array.set()
```

### Проверка ta.change()

```pine
// ✅ ПРАВИЛЬНО
if ta.change(time("D")) != 0
    // ...

// ❌ НЕПРАВИЛЬНО
if ta.change(time("D"))  // Warning: series bool вместо bool
    // ...
```
