# Верификация HighLow Levels v1.0

Дата: 2026-10-07
Статус: **код написан и отправлен на проверку в TradingView**

Pine Script компилируется и исполняется только на стороне TradingView. Из среды
разработки проверить компиляцию и поведение нельзя, поэтому ниже разделены
«проверено чтением кода» и «требует проверки на графике».

---

## Проверено чтением кода

Логика реализована и соответствует REQUIREMENTS.md:

- Шесть типов уровней: DH, DL, WH, WL, MH, ML
- Экстремумы старших ТФ запрашиваются через `request.security` с `high[1]`/`low[1]`
  и `lookahead_on` — завершённый период без перерисовки
- Границы периодов определяются через `ta.change(time("D"|"W"|"M"))`, то есть по
  часовому поясу графика
- Пересечение: `high >= price` для максимумов, `low <= price` для минимумов
- При пересечении `x2` линии фиксируется на баре пересечения, цвет меняется на
  `color.new(base, fade_alpha)`
- Объединение уровней при совпадении цены с допуском `syminfo.mintick / 2`,
  только в одном направлении, подписи склеиваются через `+`
- Фильтр по ТФ в `f_visible`: `level_rank >= f_chart_rank()`

Таблица видимости, заложенная в код:

| ТФ графика | DH/DL | WH/WL | MH/ML |
|------------|-------|-------|-------|
| 1m – 4h    | ✅ | ✅ | ✅ |
| 1D         | ✅ | ✅ | ✅ |
| 1W         | ❌ | ✅ | ✅ |
| 1M и выше  | ❌ | ❌ | ✅ |

### Найденные и исправленные проблемы

1. **Объединение одинаковых периодов** ❌→✅
   - **Проблема**: Два дневных максимума с одной ценой давали одну линию с подписью `DH+DH`
   - **Причина**: Логика объединения не проверяла, входит ли уже период в этот уровень
   - **Решение**: Добавлены флаги `hasDay`, `hasWeek`, `hasMonth` в тип `Level`; 
     при объединении проверяется, что период ещё не присутствует в уровне

2. **Объявление типа для условного лейбла** ❌→✅
   - **Проблема**: `lb = show_labels ? label.new(...) : na` может не скомпилироваться
   - **Решение**: Явное объявление типа: `label lb = na` с последующим `:=`

3. **Функция `timeframe.in_minutes()` не существует** ❌→✅
   - **Проблема**: Pine v5 не имеет функции `timeframe.in_minutes()`
   - **Причина**: Неправильное использование API TradingView
   - **Решение**: Заменено на `switch timeframe.period` с проверкой строковых значений
   - **Файл**: см. ERRORS_LOG.md для справочника функций Pine v5

4. **Линии не завершались при пересечении** ❌→✅
   - **Проблема**: Условие пересечения срабатывало, но `crossBar` не менялся
   - **Причина**: UDT передаются по значению; изменение в `array.get()` не сохранялось
   - **Решение**: Добавлено `array.set(levels, i, lvl)` после изменения поля
   - **Файл**: см. ERRORS_LOG.md раздел "Ошибка 2"

5. **Критическая ошибка архитектуры: уровни не создавались своевременно** ❌→✅
   - **Проблема**: Линии не заканчивались даже после `array.set()`, потому что их часто не было в массиве
   - **Причина**: Уровни создавались только при `new_day/new_week/new_month`, а проверка пересечения ждала их каждый бар. В большинство дней новых периодов нет, поэтому в массиве оставались старые уровни.
   - **Решение**: 
     - Создавать уровни при переходе на новый период (как и было, но логика была ошибочной)
     - Каждый бар проверять пересечение для ВСЕ уровней в массиве
     - Обновлять x2 линии каждый бар для активных уровней
   - **Файл**: см. ERRORS_LOG.md раздел "Ошибка 3"

6. **Кэширование данных вызывает зависание при масштабировании** ❌→✅
   - **Проблема**: Линии не изменяют положения при изменении масштаба по вертикали
   - **Причина**: `var` переменные хранили значение бесконечно долго
   - **Решение**: Убрано кэширование, теперь каждый бар переполучаются свежие значения через `request.security()`

## Требует проверки на графике

Это не найденные дефекты, а места, которые нельзя подтвердить без запуска.

### Компиляция
- [ ] Скрипт компилируется без ошибок и предупреждений
- [ ] UDT `Level` с полями `line` / `label` принимается компилятором
- [ ] `switch` без выражения в `f_chart_rank()` компилируется
- [ ] Объявление `label lb = na` с последующим `:=` не даёт ошибки типа

### Поведение
- [ ] На 1m видны все шесть уровней, месячные — от первого доступного бара
- [ ] На 1W дневные уровни отсутствуют, на 1M — только месячные
- [ ] Линия обрывается ровно на баре пересечения
- [ ] Пересечённые линии визуально отличимы от активных при `fade_alpha = 70`
- [ ] Совпадающие уровни дают одну линию с подписью вида `DH+WH+MH`
- [ ] Значения уровней не меняются при обновлении последнего бара (нет перерисовки)
- [ ] Поведение на инструментах с разрывами в торгах (акции на выходных, фьючерсы)

### Производительность
- [ ] Нет ошибки превышения лимита линий/подписей на 1m с большой историей
- [ ] Нет ошибки таймаута исполнения скрипта

## Открытый вопрос по семантике `lookback_depth`

В текущей реализации параметр не ограничивает, насколько далеко назад создаются
уровни: индикатор создаёт уровень на каждой границе периода по всей доступной
истории. `lookback_depth` используется только в `f_prune` как предел хранения
(`lookback_depth * 2` уровней на каждый ранг), то есть фактически работает как
«сколько последних уровней каждого типа держать на графике».

Это близко к ожидаемому поведению, но формулировка в REQUIREMENTS.md
(«глубина просмотра назад») допускает и другое чтение. Нужно подтвердить, какое
верно:

1. Держать на графике N последних уровней каждого типа — текущее поведение
2. Создавать уровни только за последние N периодов соответствующего ТФ, остальное
   не рисовать вовсе

Разница заметна на старой истории: в варианте 1 непересечённый уровень
двухлетней давности остаётся виден, в варианте 2 — нет.

## Известные ограничения

1. **Лимит объектов TradingView** — 500 линий и 500 подписей. Старые уровни
   удаляются в `f_prune`.
2. **Доступная история** — на мелких ТФ месячный уровень может начинаться раньше
   первого загруженного бара; линия рисуется от него (`startBar` остаётся 0).
3. **Часовой пояс** — берётся с графика, отдельной настройки нет (по требованию).
4. **`lookahead_on`** — корректен только в связке с `[1]`; при правке кода эту
   связку нельзя разрывать, иначе появится перерисовка.
